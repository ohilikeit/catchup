> 비개발자가 AI 코딩 툴(VSCode + Claude Code 등)로 직무 문제를 푸는 테스트의
**결과 리포트용 성향 유형 체계**. MBTI처럼 정답·우열이 없는 순수 성향 지표.
> 

---

## 0. 설계 원칙

1. **정답 없는 성향만 유형에 넣는다.** 리트머스 테스트 — *"양쪽 극단을 자기소개에 자랑스럽게 쓸 수 있는가?"* 통과한 축만 사용.
2. **품질·역량 피드백은 유형과 분리한다.** 검증·디버깅 같은 "잘했나"는 별도 *성장 팁* 블록으로, 제안 톤으로만.
3. **하드 이분이 아닌 스펙트럼.** 각 축을 0~100%로 표시해 짧은 세션의 측정 노이즈를 흡수하고 공유 욕구를 높인다.
4. **중립 네이밍.** 부정·우열 단어(안 함/대충/부족) 금지. "~형 / ~스타일"로 통일.

## 1. 4개 축

각 축은 세션의 **서로 다른 시점**에서 신호를 뽑으므로 상호 독립적이다.

| 축 | 측정 시점 | 한쪽 극 (코드) | 반대쪽 극 (코드) |
| --- | --- | --- | --- |
| **① 계획성** | 시작 전 | **P** 설계자 — 먼저 그림을 그린다 | **E** 탐험가 — 일단 부딪히며 발견한다 |
| **② 주도권** | 작업 분배·개입 | **D** 지휘자 — 단계별로 직접 끌고 가고 손도 댄다 | **G** 위임가 — 맡기고 큰 그림에 집중한다 |
| **③ 소통 방식** | 대화 중 | **S** 정밀가 — 한 번에 길고 상세하게 | **C** 대화가 — 짧게 자주 주고받으며 |
| **④ 관여 깊이** | 결과·오류 마주칠 때 | **M** 장인 — 과정·원리가 궁금하다 | **R** 실용가 — 결과·완성이 우선이다 |

→ 4글자 코드 = **16유형** (예: `PDSM`, `EGCR`).
→ 어느 쪽도 더 낫지 않다. 모든 축은 "무엇을 잘하나"가 아니라 "무엇을 선호하나"를 본다.

> **검증 축은 의도적으로 제외.** "비판적 검증 ↔ 맹목적 수용" 같은 축은 한쪽 극이 떳떳하지 못해 성향이 아니라 평가다. 검증·디버깅 품질은 §5 성장 팁으로 보낸다.

## 2. 축별 측정 규칙 (신호 정의)

플랫폼이 세션에서 자동 집계할 수 있는 신호. 각 축은 **여러 신호의 가중 합 → 0~100% 스펙트럼**으로 환산. (실제 추출 절차는 §3.)

### ① 계획성 — P(설계자) ↔ E(탐험가)

**핵심 질문:** 첫 코드 생성 이전에 준비 행동을 하는가?

- `pre_build_turns` — 첫 코드 생성/실행 요청 전까지의 대화 턴 수
- `first_prompt_type` — 첫 프롬프트가 *요구사항·구조 정의형*인가, *즉시 생성 요청형*인가 (분류)
- `planning_keywords` — "먼저 / 구조 / 요구사항 / 단계 / 계획" 등 설계 의도 표현 빈도
- `structure_sketch` — 파일·폴더·기능 목록을 미리 정의했는가 (Y/N)

> **P쪽**: 첫 행동이 계획·구조·명세. **E쪽**: 첫 행동이 곧바로 "만들어줘 / 실행해줘".
> 

### ② 주도권 — D(지휘자) ↔ G(위임가)

**핵심 질문:** 한 번에 맡기는 작업 단위가 작고, 직접 손도 대는가?

- `avg_task_scope` — 프롬프트당 요청 범위 (전체 기능 1건 vs 작은 단위 다건)
- `decomposition_count` — 작업을 잘게 나눠 순차 지시한 횟수
- `whole_delegation_rate` — "전체를 알아서 만들어줘" 류 통째 위임 프롬프트 비율
- `directive_specificity` — 후속 수정 지시가 구체적·단계적인가
- `direct_edit_events` — **에디터에서 코드를 직접 수정/타이핑한 횟수 (샌드박스)** ← *동료 표 #9 흡수.* 직접 개입↔완전 외주. 비개발자×IDE 맥락에서 특히 변별력이 큼

> **D쪽**: 작게 쪼개 단계별 지시 + 직접 손댐. **G쪽**: 큰 목표를 통째로 위임, AI에 일임.
> 

### ③ 소통 방식 — S(정밀가) ↔ C(대화가)

**핵심 질문:** 정보를 한 번에 길게 주는가, 짧게 자주 주는가?

- `prompt_length_median` — 프롬프트 길이(토큰) 중앙값
- `requirements_per_prompt` — 한 프롬프트에 담은 요구 항목 수
- `total_turns` — 전체 대화 턴 수
- `info_per_turn` — 턴당 평균 정보량
- `error_report_precision` — **에러 전달 방식: 로그·메시지 정확히 붙여넣기 vs "안 돼요" 식 증상 묘사** ← *동료 표 #5 흡수.* 정밀가↔대화가 신호

> **S쪽**: 긴 단일 프롬프트, 적은 턴, 정확한 로그 전달. **C쪽**: 짧은 프롬프트, 잦은 턴, 감각적 묘사.
(③은 ②와 다르다 — ②는 *작업 범위·개입*, ③은 *말하는 방식·정밀도*.)
> 

### ④ 관여 깊이 — M(장인) ↔ R(실용가)

**핵심 질문:** 과정·원리에 관심을 두는가, 결과물에 관심을 두는가?

- `code_read_events` — 생성된 코드를 열람/스크롤한 행동
- `why_questions` — "왜 / 어떻게 동작 / 이게 무슨 의미" 류 이해 지향 질문 빈도
- `error_response_style` — 오류 시 *원인 탐구형* 질문 vs *단순 재요청/롤백*
- `post_success_behavior` — 결과 완성 후 추가 이해·정리를 시도하나, 즉시 종료/다음 진행하나

> **M쪽**: 코드 읽기·원리 질문이 많다. **R쪽**: 결과를 받으면 빠르게 다음으로.
⚠️ `error_response_style`은 *성향 신호*로만 쓰고, 검증·디버깅 *품질*은 절대 유형에 넣지 않는다 → §5 성장 팁으로.
>

## 3. 대화 내역에서의 축 추출 설계

각 축 점수는 **두 종류 신호의 결합**으로 만든다.

- **(A) 결정적 신호 (Deterministic)** — 세션 로그에서 규칙으로 직접 계산. 세는 것·재는 것·순서. LLM 불필요.
- **(B) 의미 신호 (Semantic)** — 프롬프트 텍스트의 *의도·성격*은 규칙으로 못 잡으므로, **경량 LLM 분류기(judge)** 가 각 사용자 발화를 라벨링.

### 3.1 입력 데이터 (세션에서 뽑는 원천)

- 사용자 프롬프트 텍스트 (턴별)
- 턴 순서·타임스탬프
- AI 응답에 코드 블록 포함 여부
- 실행/도구 이벤트: 코드 실행, 파일 편집, **에디터 직접 편집(샌드박스)**, 에러 발생, 롤백

### 3.2 LLM 분류기 — 각 사용자 발화에 붙이는 라벨

한 번의 호출로 발화마다 다음 라벨을 매긴다 (배치 처리 가능):

| 라벨 | 값 예시 | 쓰이는 축 |
| --- | --- | --- |
| `intent` | 계획정의 / 생성요청 / 수정지시 / 질문 / 에러보고 | ①④ |
| `scope` | 전체위임 / 부분작업 / 단일수정 | ② |
| `specificity` | 구체·기능적 / 추상·감각적 | ③ |
| `understanding_seek` | 원리질문 있음 / 없음 | ④ |
| `error_form` | 로그첨부 / 증상묘사 / 해당없음 | ③ |

### 3.3 축별 추출 요약

| 축 | (A) 결정적 신호 | (B) LLM 라벨 | 점수화(→ 0~100%) |
| --- | --- | --- | --- |
| **① 계획성** | `pre_build_turns`, 첫 실행까지 위치 | 첫 발화 `intent`=계획정의 비율 | 준비 행동 비중 ↑ → P |
| **② 주도권** | `decomposition_count`, `direct_edit_events`, 통째위임 빈도 | `scope` 분포 | 작은 단위·직접 편집 ↑ → D |
| **③ 소통** | `prompt_length_median`, `total_turns` | `specificity`, `error_form` | 긴 발화·적은 턴·로그첨부 ↑ → S |
| **④ 관여** | `code_read_events`, 종료 속도 | `understanding_seek`, 에러 후 `intent` | 원리질문·코드열람 ↑ → M |

### 3.4 점수화 공식 (개략)

1. 각 신호를 **모집단 기준 z-score**로 정규화 (세션 길이·과제 난이도 편차 보정).
2. 축별 가중 합 → 로지스틱 변환으로 **0~100%** 스펙트럼.
3. 표본이 적은 축(특히 ④, 짧은 세션)은 **중앙(50%)으로 수축(shrinkage)** + 신뢰구간 표시.

> 원칙: **결정적 신호로 뼈대, LLM 라벨로 의미 보강.** LLM은 "분류"만 하고 "점수"는 규칙이 정한다 → 재현성·설명가능성 확보.

## 4. 16유형 이름과 한 줄 설명

| 코드 | 유형 이름 | 한 줄 설명 |
| --- | --- | --- |
| **PDSM** | 마스터 아키텍트형 | 청사진을 그리고, 직접 지휘하고, 상세히 말하고, 원리까지 파는 — 가장 손에 쥐고 가는 스타일 |
| **PDSR** | 프로젝트 매니저형 | 치밀한 계획과 정밀한 지시로 결과를 향해 곧장 직진하는 스타일 |
| **PDCM** | 장인 멘토형 | 계획은 세우되 AI와 대화하며 과정을 함께 다듬어 가는 스타일 |
| **PDCR** | 전략 디렉터형 | 큰 그림을 잡고 직접 지휘하되, 빠른 대화로 결과를 뽑아내는 스타일 |
| **PGSM** | 설계 연구가형 | 상세 설계서를 넘긴 뒤, 돌아온 결과의 원리를 들여다보는 스타일 |
| **PGSR** | 건축주형 | 꼼꼼한 명세를 한 번에 발주하고 완성품을 받아보는 스타일 |
| **PGCM** | 큐레이터형 | 방향을 잡아 맡기고, 대화로 이해하며 따라가는 스타일 |
| **PGCR** | 프로듀서형 | 방향만 정해두고 가볍게 대화하며 결과를 완성해 가는 스타일 |
| **EDSM** | 땜장이 장인형 | 일단 시작하지만, 디테일하게 직접 통제하며 깊이 파고드는 스타일 |
| **EDSR** | 현장 지휘관형 | 즉흥적으로 출발해 정밀한 지시로 빠르게 결과를 만드는 스타일 |
| **EDCM** | 탐구형 빌더형 | 부딪히며 시작하고, 대화로 통제하며 원리를 익혀 가는 스타일 |
| **EDCR** | 스프린터형 | 일단 달리고, 짧은 대화로 몰아붙여 결과를 내는 스타일 |
| **EGSM** | 실험 연구가형 | 떠오르는 대로 시작해 상세히 맡기고, 결과를 분석하는 스타일 |
| **EGSR** | 주문 제작형 | 영감이 오면 상세 주문을 넣고 결과물을 받아 드는 스타일 |
| **EGCM** | 모험가형 | 가볍게 시작해 대화로 맡기며 배워 가는 스타일 |
| **EGCR** | 마법사형 | 짧은 주문을 던지고 흐름을 타며 결과를 불러오는 스타일 |

## 5. 운영 메모

- **신뢰도 순위**: ②주도권 ≥ ③소통 > ①계획성 > ④관여. ②는 #9(직접 편집) 신호 흡수로 변별력이 더 올라감. 세션이 짧으면 ④의 표본이 적으니 스펙트럼 신뢰구간을 함께 관리.
- **상관 모니터링**: ③소통(정밀가)과 ②주도권(지휘자)이 데이터상 과하게 묶이면, 측정 신호를 *작업 범위·개입(②) vs 발화 길이·정밀도(③)* 로 더 명확히 분리.
- **성향-점수 상관 주의**: ①·②·③은 역량 점수와 양의 상관이 있어, 성향이 "점수 프록시"로 들통날 수 있음. 성향 블록엔 점수·등급 절대 비노출, ④(점수와 가장 무관)의 표현 비중 유지.
- **A/B 여지**: 3축(①②③, 8유형) 버전과 4축(16유형) 버전을 비교해 공유율·체감 정확도 측정 가능.
