# 출제 의도 (intention)

> 이 문제가 **무엇을 측정**하고, **어떤 결함을 일부러 심었으며**, 학생이 **어떤 과정으로 풀기를** 기대하는지 핵심만 적는다.

## 한 줄 의도

> "수천 행짜리 발송로그를 코드로 그룹바이해 캠페인별 성과표 + 전사 요약 한 줄로 줄인다" — **CRM 마케터의 캠페인 성과 집계 업무를 챗봇 붙여넣기로는 못 풀고(로그가 너무 길고 행 단위라) Claude Code 오케스트레이션으로만 풀리게** 만든 문제. 모든 데이터·정답은 단일 입력 `spec.csv`에서 발송로그를 합성해 생성되며, 캠페인 구성을 바꿔도 동일 구조로 재현된다.

## 측정하는 능력

| 축 | 무엇을 보는가 |
|---|---|
| **직무 능력 (마케팅 CRM)** | 발송 결과 로그를 캠페인 단위로 집계해 오픈율·클릭율·전환율·ARPU를 정의대로 산출하고, 전사 성과를 올바른 가중으로 요약하는 퍼포먼스 리포팅 감각 |
| **AI 활용 능력** | ① 원시 로그를 코드로 열어 그룹바이 ② 건수=정수·율=반올림 등 규칙을 데이터로 다뤄 일관 처리 ③ 재사용 가능한 집계 파이프라인 작성 ④ 분모0·반올림 경계·합계 검산 등 결과 검증 |
| **문제 해결력** | 긴 비정형 로그 → 집계 규칙 적용 → 정형 요약으로 환원하는 분해력. "분모 0", "X.X5 반올림 경계", "**가중평균 vs 단순평균**" 함정을 스스로 발견·처리. 어림짐작·단순평균으로 넘겨짚지 않고 정의된 식 그대로 계산하는 판단 |

> 설계 근거: [`../../../_6일반범용-마케팅-산업범용-업무형태-보강.md`](../../../_6일반범용-마케팅-산업범용-업무형태-보강.md)의 **MKT-L1-X2(이메일 캠페인 오픈·클릭·전환율 캠페인별, M(CRM)/Computed)** 를 실제 집계/분석 아키타입으로 구현하고, 분모0·반올림 경계·가중평균(Part2) 함정을 얹어 **2단계**로 끌어올린 사례. 채점은 [`_5 §6`](../../../_5직무-바이브코딩-과제설계.md)의 결정성 원칙을 따른다.

## 일부러 심은 결함 (함정)

학생이 **데이터를 곧이곧대로 계산하면 틀리도록** 설계했다. 이걸 발견·처리하는지가 변별점이다.

1. **분모 0 (발송 0건)** — 발송수가 0인 빈 캠페인이 섞여 있다(예: 오프라인 매장초대·픽업 예약안내). 율을 `오픈수/발송수`로 그냥 계산하면 0 나눗셈 오류가 나거나 칸을 비우게 된다. **정답은 모든 율=0.0, ARPU=0**(건수·합계 칸은 0). `build_dataset.py`가 `rate1(num, den)`에서 `den==0 → 0.0`으로 정의한다.
2. **반올림 경계 (X.X5)** — 일부 캠페인은 어떤 율이 **소수 둘째 자리가 정확히 5** 인 값(예: 33.25%)에 오도록 설계됐다. 반올림(round-half-up)으로 올리면 33.3, 버리거나 banker's rounding으로 내리면 33.2 — 정답과 0.1 차로 오답이 잡힌다. spec의 `round_boundary=Y` 캠페인은 `cross_check`가 **실제로 X.X5 경계에 오는지 자기검증**한다(트랩 실재성 보장).
3. **가중평균 vs 단순평균 (Part2)** — 전체 전환율을 **캠페인별 전환율들의 평균**으로 내면 오답이다. 정답은 **총전환 ÷ 총발송 (가중)** — 발송수가 큰 캠페인이 더 큰 가중을 갖는다. 발송 규모가 들쭉날쭉하게 설계돼(150~2000) 두 방식의 결과가 분명히 갈린다. 가장 핵심적인 변별 함정.
4. **퍼널 단조성 / 빈·오픈0 캠페인** — 전환수≤클릭수≤오픈수≤발송수가 항상 성립해야 한다(생성 시 fail-loud로 강제). 발송은 됐지만 오픈 0건인 캠페인(분모는 발송수>0이라 율 0.0 정상), 발송 0건인 빈 캠페인을 함께 심어, "0을 어떻게 다루는가"를 두 결로 측정한다.

> 결정성 봉쇄: 반올림이 **계산 방식에 따라 애매하게 갈리는** 항목(예: 부동소수 잡음으로 X.X49999가 되는 케이스)은 입력 설계에서 **제외**했다 — 경계 케이스는 `Decimal` 기반으로 정확히 X.X5에만 오게 합성한다. 채점은 ±0.1 허용오차로 부동소수 잡음을 흡수하되, 경계를 반대로 굴린 0.1 차는 엄격히 오답이다. 모든 케이스는 명시 규칙으로 단일 정답에 매핑되며, 정답은 항상 `spec.csv` → 발송로그 합성 → `regroup_metrics` 재집계에서 유일하게 산출된다.

## 기대하는 풀이 과정

1. **발송로그를 코드로 연다** — `발송로그.xlsx`(1행=1발송)를 읽어 `campaign_id`로 그룹바이한다. (손/챗봇 붙여넣기로는 수천 행을 일관 집계 불가)
2. **캠페인별 집계표를 만든다(Part 1)** — 건수(발송수·오픈/클릭/전환수)·합계(매출)·율(오픈율·클릭율·전환율)·평균(ARPU)을 정의대로 계산하고, **분모 0은 0.0/0으로, 율은 소수 첫째 자리 반올림**으로 정형화한다.
3. **전체 요약을 만든다(Part 2)** — 제공된 정답 집계표(`campaign_metrics_given.xlsx`)를 입력으로 총합을 내고, **전체전환율·전체ARPU는 총계로부터 가중**으로 계산한다(단순평균 금지).
4. **검증한다** — 캠페인 합계가 발송로그 행 수와 맞는지, 분모0 캠페인이 0.0으로 처리됐는지, 전체전환율이 단순평균이 아닌지 표본 점검. (검증 습관이 변별 포인트)

## 현실성 (왜 이 시나리오인가)

ESP(메일침프·Braze·자체 발송 시스템 등)는 발송마다 오픈·클릭·전환·매출 이벤트를 1행=1발송 로그로 쌓고, 마케터는 이를 캠페인 단위로 집계해 주간 성과 리포트를 만든다. **"원시 발송로그 → 캠페인 성과표 → 전사 요약"** 은 CRM·퍼포먼스 마케팅에서 매주 반복되는 실제 업무 형태이며, 특정 회사·툴에 종속되지 않은 보편 집계 과제다.

> **데이터 출처·고정성**: 캠페인별 발송·오픈·클릭·전환·매출 수치는 운영자가 단일 입력 `eval/answer_key/spec.csv`에 채운다. `build_dataset.py`가 그 spec으로 **1행=1발송 발송로그를 합성**(캠페인마다 발송수개 행, 그중 오픈수개 오픈=Y, 클릭수개 클릭=Y, 전환수개 전환=Y, 매출은 전환 행에 분배)하고, 그 로그를 **다시 그룹바이**(`regroup_metrics`)해 정답을 도출한다 — spec 숫자를 직접 베끼지 않으므로 독립검증이 성립한다. 모든 집계 지표는 발송로그에 대응 컬럼(발송수↔행 수, 오픈/클릭/전환수↔`오픈여부`/`클릭여부`/`전환여부`=Y, 매출합계↔`매출액_원`)이 있어야 계산된다(집계↔로그 교집합 불변식). **현재 spec.csv는 캠페인 50건 구성 — 정상 46건 + 발송0(빈 캠페인) 2건(C007·C008) + 오픈0 2건(C009·C010), 그중 반올림 경계 케이스 6건(C001~C006).** 발송로그·제출양식·정답키는 이 CSV **하나만 읽어** 한 번에 생성되며, 기준일 상수(`ASSIGN_DATE = 2026-06-28`, 발송일 합성용·채점 미사용)와 `random.seed(20260628)`가 고정돼 있어 **언제 재생성해도 동일**하다. 캠페인을 추가/수정하려면 `spec.csv`만 고치고 재실행하면 데이터·정답이 함께 갱신된다.
